# ADR 0013 · 실사용 우선 재정렬과 계획 1.2

- 날짜: 2026-09-29 KST
- 상태: 채택 — 사용자의 전체 설계·방향 검토 후 진행 지시
- 기준: main `82be8d8`, 계획 1.1(ADR 0012)

## 배경

계획 1.1은 기능별 세로 완결을 원칙으로 했지만 실제 진행은 BE-01–20(P2–P7 백엔드)을 먼저 닫고 업무 웹은 FE-01–02 spike에 머물렀다. P2 gate(QA-03)와 P3 gate(QA-04)가 열려 있고 사용자 ACCEPTED 카드는 없다. 제품의 가장 큰 불확실성인 "매일 쓰게 되는가"와 "판단 보조가 실제로 도움이 되는가"는 계획상 P3·P9에서야 검증된다. CORE-16은 실제 기록이 없어 BLOCKED였고, 실제 기록은 화면이 없어 쌓을 수 없었다.

## 결정

1. **다음 목표는 직접 매일 쓸 수 있는 얇은 앱이다.** FE-03 → FE-04 → QA-03 → FE-05–10 → QA-04를 우선한다. 화면을 붙이며 드러난 백엔드 계약 결함은 해당 BE 카드의 반례와 증거를 갱신해 고친다.
2. **백엔드 기능 확장을 QA-04까지 동결한다.** BE-21(현재 구현 범위에서 일시 중단)·BE-22·BE-23·BE-26에 QA-04 선행을 추가했다. BE-24·BE-25·QA-08은 이 카드들을 통해 함께 뒤로 간다.
3. **판단 효용 평가를 앞당긴다.** CORE-16을 P4의 "실사용 자료의 관련 맥락 제안 효용 평가·판단 확장 결정"으로 바꾸고 선행을 CORE-10·FE-12·QA-04로 한다. 결과로 제안 정책과 P5 구조 보조·P6 모델 정제 확장 여부를 정한다. 구조 보조 UI(FE-14)와 QA-06은 CORE-16 뒤에 온다. 구조 변경·글 정제의 실제 효용 측정은 QA-06으로 옮긴다.
4. **실사용 전 최소 백업.** QA-04에서 실제 자료를 넣기 전 로컬 DB·파일 volume 백업과 빈 DB 복원을 1회 확인한다. 이것은 BE-24 운영 backup 완료가 아니다.
5. **백엔드 계층 규칙을 코드 현실에 맞춘다.** 필수 경계는 `controller → backend 기능 모듈 → domain/core`다. controller는 HTTP 변환·인증 문맥만 다루고 SQL·transaction을 갖지 않는다. port/infrastructure 분리는 provider·파일 저장소·clock처럼 교체나 격리가 필요한 경계에 둔다. 모든 기능 모듈에 application/ports/infrastructure 폴더를 강제하지 않는다. 1,000줄을 넘는 소스 파일은 수정할 때 기능 단위로 나눈다. `packages/backend/src/data-transfer/service.ts`는 BE-21 재개의 첫 작업으로 분할한다.
6. **상태 서술은 한 곳에 둔다.** 카드 상태의 정본은 backlog.json, 사람이 읽는 요약은 `docs/status/project-state.md` 하나다. README·AGENTS·계획 README·07·09는 카드 상태를 반복하지 않고 링크한다.

## 유지하는 것

카드 75개·P0–P9 구간·ADR 0012의 main 직접 작업 규칙, 원본·출처·권한·공개 경계·디자인 불변식은 바꾸지 않는다. 운영 계열 카드를 삭제하지 않고 순서만 늦춘다. 완료 기준을 낮추거나 상태명을 바꿔 미완성을 숨기지 않는다.

## 결과와 한계

착수 가능한 카드는 FE-03·QA-01·QA-02다. QA-01은 핵심 경계 검사를 CI 실패로 연결하는 최소 범위로 유지한다. 실사용 기간과 표본 규모는 CORE-16 착수 시 실제 누적량을 보고 정하며, 짧은 기간의 편향을 보고서에 적는다.
