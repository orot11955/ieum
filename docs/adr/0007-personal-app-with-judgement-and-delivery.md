# ADR 0007 · 이음은 개인 관리 앱이며 판단 코어와 발행 API를 포함한다

- Status: Accepted
- Date: 2026-09-22
- 근거: 사용자의 제품 범위 보완
- 보완 대상: Core Lab 중심 설명이 제품 전체로 오해될 수 있던 범위 표현

## Context

사용자가 의도한 이음은 일정·생각·경험·외부지식을 입력하여 정리하고, 일정·할일·위키 등 개인 저장소를 관리하며, 축적한 자료와 여러 관점을 바탕으로 문서를 만들고 API로 발행하는 개인 내부 웹·앱이다. 외부 블로그 화면은 API 계약을 따라 별도로 만든다.

제로베이스 검토는 판단 실험의 규모를 줄였지만, 웹 UI를 선택 사항으로 표현하고 일정·할일을 단순 투영으로 설명하며 발행을 단순 export까지만 설명해 제품 전체 경계가 불명확해졌다.

## Decision

1. 이음 제품에는 내부 관리 프론트엔드, 관리 백엔드, 개인 저장소, 선택적으로 호출되는 Judgement Core, 문서 작성·발행 관리, Delivery API가 포함된다.
2. 일정·할일·위키는 실제 상태와 편집 흐름이 있는 관리 기능이다. 캘린더·보드는 해당 데이터의 뷰다. 통합 기록 풀은 단일 테이블을 의미하지 않는다.
3. Core는 일부 정리·연결·구조화·파생 판단을 맡는다. 명시적인 저장·편집·완료·발행 명령과 권한/트랜잭션은 애플리케이션 계층이 담당한다.
4. 문서의 작성·정제·검토·발행은 이음 안에서 수행한다. 공개 독자용 블로그 화면은 별도 클라이언트로 둔다.
5. Delivery API는 승인된 발행 snapshot만 제공한다. 비공개 기록·초안·관리 API·DB를 외부 블로그에 직접 노출하지 않는다.
6. CLI Core Lab과 선택적 Lab Inspector는 초기 실험 수단이다. 최종 제품에 내부 UI나 발행 API가 없다는 의미로 해석하지 않는다.

## Scope interpretation

기존 Core/Lab 문서의 `UI 후순위`, `블로그 편집기 제외`, `외부 발행 제외`, `선택적 Lab UI`는 M0/M1 판단 실험에 한정한다. 문서 편집과 승인 발행을 최종 제품에서 제외하는 규칙은 아니다. 자동 공개 발행 금지와 사용자의 명시적인 Publish 명령은 구분한다.

제품 전체의 최신 범위는 [제품 목적](../product/vision-and-scope.md)과 [내부 앱·발행 경계](../architecture/application-and-publishing.md)를 따른다. Core의 순수 TS·시점 기반 Replay·점수/확률 분리·승인 원칙은 유지한다.

## Consequences

제품 검증은 CLI의 검색 점수만으로 끝나지 않는다. 내부 UI에서 실제 일정·할일·위키를 관리하고 문서를 작성·발행하며, 별도 소비자가 API로 공개본을 표시할 수 있어야 한다. Core 장애 시에도 명시적인 관리 기능이 유지되어야 한다.

이 결정은 기능 범위의 확정이지 한 번에 모든 기능을 구현하라는 지시가 아니다. 네이티브 앱, 멀티유저 협업, 외부 캘린더 동기화, 별도 분산 서버는 자동으로 추가하지 않는다.
