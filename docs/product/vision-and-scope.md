# 제품 목적과 범위

- 개정: 2026-09-22
- 상태: 실험을 위한 제품 정의. 사용자 효용은 아직 검증하지 않았다.

## 1. 풀려는 문제

기록은 남지만 이전에 왜 그런 생각을 했는지, 무엇이 바뀌었는지, 어떤 근거로 결론에 도달했는지 다시 구성하기 어렵다. 기록 도구·프로젝트 도구·글쓰기 도구 사이에서 동일한 생각을 다시 정리하는 수고를 줄이는 것이 이음의 가설이다.

목표 행동은 `기록 → 관련 흐름 재발견 → 비교·수정 → 결정/행동/정리본 → 다시 기록`이다. 모든 기록을 반드시 분류하거나 결과물로 바꿔야 하는 것은 아니다.

## 2. 반드시 보존할 요구

일정은 행동을 보는 하나의 투영일 뿐 시스템의 중심이 아니다. 블로그는 외부 부가기능이 아니라 생각과 근거에서 나온 결과물이다. 공개된 글이 생겨도 그 이전의 질문·반론·실험·결정은 남아야 한다.

원본은 기록자가 실제로 남긴 내용의 증거이지, 그 내용이 참이라는 보증이 아니다. 사용자 관찰, 해석, 잠정 가설, 타인 자료를 구분하고 확인되지 않은 내용을 자동으로 확정하지 않는다.

한 기록을 여러 맥락에서 활용할 수 있어야 한다. 폴더 하나를 정답으로 정하는 분류기가 되어서는 안 된다. 흐름의 이름과 경계는 바뀔 수 있지만 출처와 변경 이력은 보존한다.

## 3. 사용자에게 보이는 최소 개념

| 개념 | 의미 | 비고 |
| --- | --- | --- |
| 기록 Capture | 원문과 수집 당시 출처 | 수정은 새 revision |
| 생각 단위 ThoughtUnit | 참조 가능한 발췌/생각 | 초기에는 기록당 하나가 기본 |
| 맥락 Context | 함께 보는 이유와 범위 | 폴더·정답 클래스와 다름 |
| 연결 Membership / Relation | 맥락 소속 또는 생각 간 관계 | 서로 다른 관계이며 혼용하지 않음 |
| 제안 Proposal | 사용자가 검토할 변경안 | 원본을 바꾸는 사실과 구분 |
| 결과물 Artifact | 결정 정리, 문서, 초안 등 | revision별 출처 연결 |

`Seed`, `Locus`, `Thread`, `Synthesis`를 동시에 별도 영속 엔터티로 추가하지 않는다. 이전 논의의 Seed는 Capture에, Locus는 Context에 대응시키고 Thread는 흐름을 보여주는 뷰로 취급한다. Synthesis는 파생 과정이지 별도 코어 계층이 아니다. 새 엔터티는 독립적인 생명주기와 제약이 확인될 때 추가한다.

## 4. 첫 사용자 흐름

예시는 합성 시나리오다.

`설정을 여러 장비에서 공유하면 반복 작업을 줄일 수 있겠다`를 기록한다. 이음은 기존의 `개발 환경 관리`와 `설정 배포 방식`을 함께 후보로 보여주고, 어떤 기존 기록과 연결되는지 제시한다. 사용자는 둘 다 연결하거나, 하나만 연결하거나, 아무것도 선택하지 않을 수 있다.

뒤이어 `중앙 서버가 중단되면 로컬 실행도 막힐 수 있다`는 반론이 들어온다. 같은 주제의 반론이라는 이유로 관계를 끊지 않는다. 이후 정리 재료에는 원래 제안과 반론, 확인한 결과, 아직 열린 질문이 함께 포함된다.

사용자가 글을 만들 때 시스템은 그 자료를 구조화하고 문장별 출처를 유지한다. 승인받지 않은 사실을 추가하거나 자동으로 공개하지 않는다.

## 5. 서로 다른 세 가지 판단

**연결 판단:** 관련 맥락들을 제안한다. 빠르게 응답하되 입력을 이해하기 어려우면 보류한다. 대표 맥락 선택은 별도 문제다.

**구조 판단:** 너무 넓어진 맥락, 서로 다른 목적, 중복된 맥락을 검토한다. 병합 외에 유지·연결·상위 맥락 생성도 대안이다. 분리 시 모든 기록을 강제로 하나의 자식으로 보내지 않는다.

**파생 지원:** 특정 목적과 독자를 위해 무엇을 정리할지 구성한다. 글을 만들기 전에 반드시 결정이 끝나야 하는 것은 아니다. 열린 질문이나 실패한 실험도 유효한 글감이다.

이 셋을 하나의 가중치나 하나의 confidence로 해결하지 않는다.

## 6. 첫 실험 범위와 제외

첫 실험은 로컬 CLI에서 기록을 입력하고 관련 후보를 확인하고 선택 결과를 남기며 출처가 있는 정리 재료를 내보내는 작은 흐름이다. 읽기·추론·승인 명령은 구분한다.

멀티유저 SaaS, 캘린더 동기화, 알림, 블로그 편집기, 외부 발행, 범용 플러그인 플랫폼, 완전한 지식 그래프, 모델 학습 인프라는 초기 범위에서 제외한다. UI나 에이전트 수를 늘려 판단 성능의 부재를 가리지 않는다.

## 7. 제품 성공과 실패

좋은 후보를 보여주는 것뿐 아니라 사용자가 이전 생각을 찾는 시간이 줄고, 연결 이유를 이해하고, 잘못된 연결을 쉽게 되돌리며, 정리 재료를 실제로 재사용해야 한다.

추천을 거의 하지 않아 정밀도만 높은 시스템, 매번 승인을 요구해 기록보다 관리가 더 번거로운 시스템, 많은 기록을 그럴듯한 글로 바꾸면서 근거를 잃는 시스템은 실패다.

품질이 부족하면 기능을 더 붙이는 대신 실패를 검색·라벨 정의·의미 표현·경계 판단·사용자 효용으로 분해한다. lexical 실패는 전체 개념의 실패도, 임베딩 도입 금지의 근거도 아니다.

실험 정의는 [Core Lab 계획](../plan/core-lab-experiment-plan.md), 구현 개념은 [도메인 모델](../architecture/domain-model.md)을 따른다.
