# 제품 목적과 범위

- 개정: 2026-09-22, 내부 관리 앱 및 발행 API 범위 보완
- 제품 방향: 사용자 요구에 따른 기준
- 세부 기능·구현 순서: 설계안이며 아직 구현·검증하지 않았다.

## 1. 이음의 정의

이음은 **일정·생각·경험·외부지식 등을 기록하고 정리하여 개인의 일정·할일·위키·지식 저장소를 관리하며, 그 자료에서 통찰이 담긴 문서를 만들어 발행하는 개인 내부 관리 웹·앱**이다.

판단 Core는 이음 전체가 아니다. 일반적인 저장·편집·상태 관리·권한·발행 기능은 앱의 업무 기능이 담당하고, 의미를 해석하고 연결하거나 파생을 제안해야 하는 일부 작업을 Core에 맡긴다.

발행한 문서는 이음의 API로 제공한다. 이를 블로그처럼 보여주는 외부 사이트는 API 계약을 기준으로 별도로 구현한다. 이음이 백엔드만 제공한다는 뜻은 아니며, **내부 사용자 앱은 이음에 있고 외부 독자용 블로그 화면은 이음 밖에 있다.**

## 2. 사용자 흐름

```text
일정 / 생각 / 질문 / 경험 / 외부 자료 입력
  → 원본·출처가 있는 개인 기록 풀
  → 정리·연결·구조화와 사용자의 확인/수정
  → 일정·할일·위키·경험·프로젝트를 내부 앱에서 관리
  → 여러 기록·경험·관점을 비교하고 통찰을 정리
  → 문서 작성·편집·근거 검토
  → 공개할 문서 버전 발행
  → Delivery API 제공
  → 외부 블로그·공개 사이트의 독자 화면
```

일정을 직접 등록하거나 위키 문서를 바로 쓰는 것도 정상 흐름이다. 모든 입력을 자유 텍스트로 변환한 뒤 AI가 다시 해석해야 하는 것은 아니다. 모든 기록을 문서나 공개 글로 승격할 필요도 없다.

일정 실행과 할일 완료에서 나온 결과·경험은 다시 기록 풀에 연결한다. 따라서 흐름은 일방향 수출이 아니라 `기록 → 관리/행동 → 경험 → 지식/문서 → 새 생각`으로 이어진다.

## 3. 제품의 세 영역

| 영역 | 이음에 포함되는 책임 | 경계 |
| --- | --- | --- |
| 개인 관리 앱 | 기록함, 일정·할일, 위키·경험, 맥락·관계, 검색, 문서 작성·발행 관리 | 사용자 인증이 필요한 내부 웹·앱 |
| 판단·정제 보조 | 추출 후보, 관련성, 묶기·나누기 제안, 근거 선택, 통찰 문서의 정리 보조 | 일반 CRUD를 대신하지 않는 일부 기능 |
| 발행·제공 | 검토한 문서 버전 발행, 공개본 관리, Delivery API 계약 | 외부는 공개 허용된 데이터만 조회 |

외부 블로그의 테마·페이지·레이아웃·렌더링·독자 경험은 별도 클라이언트의 책임이다. 멀티유저 협업 서비스나 블로그 테마 플랫폼을 당장 만들겠다는 뜻이 아니다.

## 4. 일정·할일·위키는 실제 관리 대상이다

기존 표현인 `일정은 하나의 투영`은 캘린더 화면의 설명으로만 사용한다. 일정 자체는 시각·시간대·변경·취소 상태를 갖고, 할일은 완료·보류·기한 상태를 갖는다. 위키는 사용자가 편집하는 본문과 revision을 갖는다. 이들은 맥락에 붙은 태그나 검색 결과만으로 대체되지 않는다.

한 기록에서 할일과 위키 근거가 함께 나올 수 있지만, 생성된 할일과 위키는 각자의 생명주기를 가진다. 원문을 고쳤다고 완료한 할일을 다시 열거나 공개 문서를 자동 덮어쓰지 않는다. 원본·개인 관리 항목·결과물은 출처 참조로 연결한다.

`기록 풀 하나`는 정보가 끊어지지 않는 제품 개념이다. 모든 데이터를 하나의 테이블이나 범용 JSON 구조에 넣으라는 요구가 아니다.

## 5. 정리와 자동화의 의미

입력하면 시스템이 정리 방향을 만들고 반복적인 수작업을 줄이는 것이 목표다. 단순히 검색 후보만 보여주는 도구를 최종 제품으로 삼지 않는다.

명시적인 일정 폼 저장, 할일 완료, 위키 수정, 사용자의 발행 명령은 앱이 직접 처리한다. 자유 기록 속 약속/행동/개념 추출, 관련 맥락 추천, 분리·병합, 문서 초안은 해석이 필요한 작업이므로 선택적으로 Core·모델 보조를 사용한다.

첫 실험에서 제안 중심으로 검증하는 것은 제품 목표를 수동 관리로 바꾼다는 뜻이 아니다. 검증되지 않은 해석을 되돌리기 어려운 변경에 바로 적용하지 않는다는 뜻이다. 자동화 수준은 작업 종류·가역성·사용자 의도에 따라 달리 정하고, 기본적인 개인 관리 기능을 매번 모델 응답에 묶지 않는다.

## 6. 여러 관점에서 문서를 만든다

문서는 자신의 기록을 단순 요약하는 것에 한정하지 않는다. 본인의 경험과 실험, 외부 자료의 주장과 반론, 여러 사람의 관점 등을 함께 검토하여 비교·해석·통찰이 담긴 문서를 만들 수 있어야 한다.

외부 저자, 자료 출처, 내 경험, 내가 내린 해석, 모델의 재서술을 구분한다. 자료 여러 개가 같은 원문을 재인용했다면 독립된 근거 여러 개로 세지 않는다. 모델이 만들어 낸 관점을 실존 인물의 발언으로 표기하지 않는다.

`여러 사람의 통찰`을 다룬다는 이유만으로 여러 사용자의 비공개 저장소를 결합하는 협업 SaaS를 필수 범위에 넣지 않는다. 초기에는 한 사람의 개인 저장소에 허용된 외부 관점과 출처를 모아 문서화하는 흐름으로 구현할 수 있다.

## 7. 원본·정제·발행의 경계

원본은 작성 당시의 내용과 출처를 보존한다. 정제 결과는 원본을 덮어쓰지 않는다. 하나의 기록은 여러 맥락에서 쓰일 수 있으며, 연결되지 않은 상태도 정상이다. 원문이나 사용자의 승인은 그 내용이 참이라는 보증이 아니다.

내부 위키나 문서의 초안을 수정해도 이미 발행한 글은 바뀌지 않아야 한다. 공개본은 검토한 특정 문서 버전에서 만들고, 공개하도록 선택한 본문·메타데이터·출처·첨부만 포함한다. 내부 원문과 비공개 근거 묶음은 자동으로 공개하지 않는다.

사용자는 이음 내부에서 발행·개정·철회를 관리한다. 외부 블로그는 Delivery API에서 제공되는 발행본을 표시하며, 내부 상태나 데이터베이스 구조에 의존하지 않는다.

## 8. Core Lab과 제품 범위

Core Lab은 판단 알고리즘의 가능성을 먼저 검증하는 실험이다. M0/M1에 DB·웹·발행 API를 넣지 않는 이유는 작은 실험을 위해서이지 최종 제품에서 제외하기 위해서가 아니다.

내부 관리 웹은 제품 단계의 필수 산출물이다. 별도 네이티브 앱·오프라인 동기화 방식은 아직 결정하지 않으며, 우선 웹 중심으로 경험을 검증한다. 판단 후보를 관찰하는 Lab Inspector는 실제 사용자가 일정·위키·문서를 관리하는 앱을 대신하지 않는다.

초기 실험 제외: 생성형 모델 필수 의존, 외부 캘린더 동기화, 자동 Split/Merge, 자동 공개 발행, 네이티브 앱 동시 개발, 멀티유저 SaaS.

최종 제품 포함: 내부 관리 UI, 일정·할일·위키, 기록 정리 보조, 문서 작성·정제, 사용자 승인 발행, Delivery API.

제품 밖: 별도로 만드는 외부 블로그의 화면과 운영. 테스트용 Delivery 소비자는 구현할 수 있지만 이음에 외부 블로그를 결합시키지 않는다.

## 9. 성공의 의미

기록과 정리가 실제로 쉬워져야 하며, 일정·할일·위키가 일상에서 유용하게 관리되어야 한다. 축적한 경험·외부지식을 근거 있는 문서로 재사용하고, 같은 발행 API 계약을 이용하는 별도 블로그에서 공개본을 보여줄 수 있어야 한다.

판단 정확도만 높거나 CLI Replay만 통과해도 제품이 완성된 것은 아니다. 수동 기본 기능의 완성, 판단 보조의 유효성, 문서 정제의 효용, 공개 경계의 안전성을 각각 평가한다.
