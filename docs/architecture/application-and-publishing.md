# 내부 앱 · 업무 기능 · 판단 코어 · 발행 API

- 개정: 2026-09-22
- 상태: 제품 경계는 사용자 요구 기준. 세부 모듈·필드·API 경로는 제안이며 아직 구현하지 않았다.

## 1. 제품의 경계

이음은 내부 프론트엔드와 백엔드를 가진 개인 관리 제품이다. Headless 방식인 것은 **외부 독자용 발행 채널**이지 이음 전체가 아니다.

```text
IEUM 내부 사용자 웹·앱
  → 관리 API / Application Services
      ├─ 기록·자료·출처
      ├─ 일정·할일
      ├─ 위키·맥락·개인 지식
      ├─ 문서 작성·revision·정제
      └─ 승인·발행·철회
           │ 필요한 의미 판단만 요청
           └─ Judgement Core / 선택적 모델 어댑터

개인 저장소 → 검토한 문서 버전 → 공개용 Publication
                                    ↓
                            IEUM Delivery API
                                    ↓
                          별도 외부 블로그·사이트
```

외부 블로그는 DB나 관리 API를 사용하지 않는다. 내부 앱과 Delivery API는 같은 코드베이스·프로세스·DB에서 시작할 수 있다. 논리적 책임·권한·응답 스키마 분리가 여러 서버나 별도 하네스를 의미하지 않는다.

## 2. 내부 앱의 실제 사용 공간

화면 명칭은 설계 예시이며 고정된 메뉴 개수가 아니다.

| 공간 | 사용자 행동 | 선택적으로 맡길 판단 |
| --- | --- | --- |
| 기록함 | 일정·생각·경험·외부자료 기록, 편집, 출처 확인 | 의미 단위/행동/주제 후보 추출 |
| 일정·할일 | 일정 등록·변경, 기한 관리, 완료·보류 | 기록에서 일정/할일 후보 발견, 중복 가능성 |
| 위키·지식 | 문서 작성·편집, 관련 경험/자료 조회 | 연결·중복·모순 후보, 갱신 제안 |
| 맥락·프로젝트 | 기록 묶음과 실행 흐름 관리 | 관련성, 분리·병합, 상위 맥락 제안 |
| 문서 작업실 | 자료 모으기, 비교·정리, 초안·revision 작성 | 근거 선택, 관점 비교, 문장 정제 보조 |
| 발행 관리 | 미리보기, 공개 필드 확인, 발행·개정·철회 | 개인정보/출처 누락 가능성 보조 검사 |

검토용 Lab Inspector는 개발 도구다. 실제 내부 앱을 대신하지 않으며 최종 제품 UI를 선택 사항으로 만들지 않는다. 우선 웹 중심으로 구현하고 모바일 화면을 고려한다. PWA·네이티브 앱·완전한 오프라인 동기화는 별도 기술 결정으로 남긴다.

## 3. 앱의 결정과 Core의 판단

| 명령/질문 | 책임 | Core 응답을 기다려야 하는가? |
| --- | --- | --- |
| 이 시간에 일정 저장 | Calendar application service | 아니오 |
| 이 할일 완료 | Task application service | 아니오 |
| 위키 본문 수정 | Wiki application service | 아니오 |
| 이 검토 버전을 발행 | Publishing application service | 아니오; 권한·revision·공개 검증은 필요 |
| 이 자유 기록에 할일이 있는가? | 추출 보조와 Core 정책 | 제안을 사용할 때만 |
| 어떤 기록·맥락과 관련 있는가? | Routing Core | 해당 추천 기능에서만 |
| 묶음을 나누거나 합칠까? | Structure Core | 변경 제안에서만 |
| 어떤 근거로 글을 구성할까? | 자료 검색·파생 보조 | 선택한 보조 기능에서만 |

Core의 점수가 높아도 권한 검증이나 도메인 불변식을 우회할 수 없다. 명시적인 사용자 입력을 다시 모델이 허가하도록 만들지 않는다. 수동 문서 작성과 발행은 모델 없이 가능하며, 출처/형식/공개 범위 검사도 생성형 추론 없이 수행할 수 있어야 한다.

Core가 의미적 후보를 반환하면 애플리케이션 계층이 사용자 의도·자동화 정책·현재 revision을 확인하여 변경 명령을 실행한다. Core가 ORM 객체를 수정하거나 발행 URL을 직접 생성·공개하지 않는다.

## 4. 개인 저장소의 도메인 확장

기존 [도메인 모델](domain-model.md)은 기록·판단·출처 계약이다. 아래는 제품 단계에서 추가할 실제 관리 객체의 최소 설계다.

| 객체 | 고유 상태 | 원본과의 연결 |
| --- | --- | --- |
| Task | title, status, dueAt?, completedAt?, revision | originRefs와 ContextMembership; 원문은 그대로 보존 |
| CalendarEvent | startsAt/endsAt 또는 all-day date, timeZone, status, revision | 기록에서 추출하거나 직접 등록 |
| WikiDocument | title, body revision, links, review state | 기록·외부자료·경험을 근거로 참조 |
| Document / Artifact | draft, revision, purpose, claim/source mapping | 여러 기록과 위키를 함께 참조 |
| Publication | public identity, 선택된 revision, 공개 projection, 상태 | 검토된 문서 revision을 고정 |

WikiDocument와 Document가 동일한 편집/revision 구현을 공유할 수는 있다. 첫 구현에서 별도 엔진을 중복 생성하지 않는다. 반면 Task/CalendarEvent의 상태·제약을 범용 Artifact JSON에만 숨기지 않는다. 본문 위키의 갱신과 작업 완료는 서로 다른 명령이다.

캘린더·보드·타임라인은 뷰다. 일정·할일 자체는 상태를 갖는 도메인이다. 통합 기록 풀은 하나의 거대한 테이블이 아니라 출처·맥락으로 이어지는 정보 구조다.

자유 기록에서 추출하는 후보에는 원본 revision/span, 추출 버전, 종류, 명확한 값과 미확인 값, proposal ID를 남긴다. 동일 제안을 다시 수락해 Task/Event가 중복 생성되지 않게 한다. `다음 주에 해보자`처럼 시각·의도가 모호하면 임의의 확정 일정으로 만들지 않는다.

원문 수정은 이미 승인된 Task를 자동 취소하거나 완료 상태를 뒤집지 않는다. 새 변경 후보로 연결하고 사용자가 정정할 수 있게 한다. 작업 결과·경험을 추가하면 다시 원래 기록/프로젝트/위키에 연결한다.

## 5. 구체적인 사용 예

다음은 합성 입력이다.

> 금요일 오후에 캐시 설정을 시험해 보자. 지난 테스트에서는 응답이 나아졌지만 다른 자료에서는 오래된 데이터 문제를 지적했다.

처리할 수 있는 결과는 하나의 라벨이 아니다. 원문을 보존하고, `캐시 설정 시험`이라는 할일 후보, 사용자가 날짜·시간을 확인한 일정, 지난 테스트의 경험, 외부 자료의 반론을 서로 연결한다. `캐시 운용` 위키에 관련 근거를 추가할지 제안한다.

이후 실제 시험 결과를 기록하면 경험이 보강된다. 사용자는 자기 결과와 외부의 상반된 관점을 바탕으로 `캐시 성능과 데이터 일관성의 선택`이라는 문서를 작성할 수 있다. 문서는 원문을 모아 놓은 목록이 아니라 비교·해석·주장을 담을 수 있지만 어떤 부분이 내 경험인지, 외부 주장인지, 새 해석인지 구분한다.

문서를 발행하면 공개하도록 선택한 내용만 Publication으로 만든다. 외부 블로그가 이 공개본을 API로 가져와 보여준다. 개인 일정과 원래 시험 메모는 자동 공개되지 않는다.

## 6. 문서 작성과 공개 발행

```text
개인 기록/자료/위키
  → 자료 묶음과 통찰 정리
  → Draft 편집
  → 내용이 고정된 DocumentRevision
  → 출처·개인정보·공개 범위 검토 / READY
  → 사용자 Publish 명령
  → Publication의 공개 snapshot
  → Delivery API
```

READY는 검토 가능한 특정 버전의 워크플로 상태다. 모델이 높은 점수를 냈다는 뜻이나 모든 주장이 사실이라는 보증이 아니다. Draft나 임시 checkpoint를 바로 공개하지 않는다. 글이 새로 수정되면 새 revision을 검토하고 발행해야 한다.

공개 snapshot에는 해당 발행 버전의 본문·제목·요약·slug·공개 author 정보·공개 태그·공개 출처·승인된 첨부만 포함한다. 별도 private source mapping은 내부에 남긴다. 내부 DocumentRevision을 그대로 JSON 직렬화한 뒤 필드 몇 개를 지우는 대신 공개 필드를 명시적으로 선택한다.

내부 문서 수정은 현재 공개본에 영향을 주지 않는다. 기존 공개본의 개정은 새로운 공개 revision을 만든 뒤 현재 버전 포인터를 원자적으로 바꾼다. 철회 시 제공을 중단하고 이력은 내부에 남긴다. 공개 snapshot이 불변이라는 사실은 철회된 버전을 계속 공개해야 한다는 뜻이 아니다.

## 7. 두 API의 계약

아래 경로는 설명용 초안이다. 실제 endpoint 구현과 OpenAPI 파일은 아직 없다.

| API | 소비자 | 예시 경로 | 접근 데이터 |
| --- | --- | --- | --- |
| Management API | 이음 내부 웹·앱 | `/api/v1/tasks`, `/api/v1/wiki`, `/api/v1/documents`, `/api/v1/publications` | 인증된 개인 데이터, 편집/승인 명령 |
| Delivery API | 외부 블로그·사이트 | `/delivery/v1/publications`, `/delivery/v1/publications/{id}` | 해당 소비자에게 제공 가능한 발행본만 |
| Preview API | 인증된 내부 미리보기 | 관리 API의 preview 경로 | 지정된 미발행 revision; 공개 캐시 금지 |

Delivery 목록에는 정해진 정렬·페이지네이션·요약 필드를, 상세에는 publication ID, public revision, title, slug, body, bodyFormat, publishedAt, updatedAt와 승인된 공개 메타데이터를 제공하는 것으로 시작한다. raw Capture, 전체 claimMap, private source IDs, 개인 일정/할일, draft와 내부 판정 trace는 포함하지 않는다.

초기 bodyFormat은 Markdown 하나로 제한하는 안을 우선 검토한다. 실행 코드를 담는 MDX나 소비자마다 다른 렌더링 가정은 기본 계약에 넣지 않는다. 사용하는 Markdown dialect·HTML 처리·이미지/링크 표현은 계약에 명시하고, 소비자도 안전한 렌더링을 수행해야 한다.

OpenAPI로 입력/응답 schema, 오류, 인증 범위, 페이지네이션, 정렬, 누락 가능한 필드와 버전 정책을 명시한다. 이는 구현 언어나 내부 DB 구조 없이 외부 소비자가 계약을 알도록 하기 위한 선택이다. [OpenAPI 공식 사양](https://spec.openapis.org/oas/v3.2.0.html)

실제 사양 버전은 사용 도구와의 호환성을 검증한 뒤 고정한다. 문서에 사양 링크가 있다는 이유로 OpenAPI contract가 이미 구현되었다고 보고하지 않는다.

## 8. 권한·캐시·철회 경계

내부 앱은 사용자 인증과 소유 범위 검증을 한다. Delivery는 발행된 것만 반환하며, API key를 사용하는 배포라면 외부 블로그의 서버/빌드 환경에 읽기 전용 자격증명을 둔다. 관리 권한을 재사용하거나 서버용 비밀을 브라우저 bundle에 넣지 않는다. 공개 브라우저 호출이 필요하면 비밀이 없는 명시적인 공개 읽기 경로를 별도로 설계한다.

Preview는 인증과 revision 범위를 확인하고 `Cache-Control: no-store`를 기본안으로 한다. 공개 Delivery의 ETag/조건부 조회·캐시 정책은 발행 revision과 공개 상태를 함께 고려한다. 캐시 지시자와 재검증의 의미는 [HTTP Caching RFC 9111](https://httpwg.org/specs/rfc9111.html)을 따른다.

철회 후 원본 API에서 접근을 차단해도 외부 블로그의 정적 빌드·CDN·브라우저 사본까지 자동 회수된다고 약속하지 않는다. 소비자는 철회 반영 기한, 재조회/재빌드, 필요 시 webhook/purge 절차를 계약해야 한다. 최초 계약에서는 이러한 갱신·철회 동작을 검증하기 전까지 외부 배포 완료로 보지 않는다.

본문뿐 아니라 이미지·첨부에도 공개 승인과 철회 정책이 필요하다. 내부 파일의 URL을 그대로 공개본에 넣지 않는다. 과거 공개 revision이나 직접 asset URL로 철회를 우회할 수 있는지도 검사한다.

## 9. 구현과 실험을 구분한다

코어 첫 실험 M0/M1은 CLI로 유지한다. 제품 구현에서는 내부 사용자 화면과 관리 기능, 문서 편집·발행, Delivery API를 실제로 구현해야 한다. 이들은 Core Lab의 부록이 아니라 제품 산출물이다.

제품의 모듈은 한 애플리케이션 안에서 시작한다. 외부 블로그는 별도 저장소/클라이언트로 API를 소비할 수 있으며 내부 TypeScript 타입을 공유하지 않아도 작동해야 한다. 검증용 소비자 하나로 계약을 시험할 수 있지만 그 UI를 이음의 필수 런타임으로 묶지 않는다.

제품 최소 검증은 `내부 앱에 기록 → 일정/할일/위키 관리 → 문서 작성 → 검토·발행 → API로 조회`이며, 판단 보조를 껐을 때도 명시적 작업이 가능해야 한다. 외부 블로그는 목록·상세·개정·철회가 계약대로 반영되는지 확인한다. 자세한 단계는 [실험·구현 계획](../plan/02-core-plan.md)을 따른다.
