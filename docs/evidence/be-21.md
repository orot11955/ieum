# BE-21 · 개인 Import/Export·dry-run·중복 처리

상태: **진행 중**. 선행 BE-07·BE-11·BE-18·BE-06은 VERIFIED다. 현재 구현·검증 범위는 Capture 원문의 revision 이력, Context·Task·Event의 현재 상태, 저장된 Task 상태 전이와 Task 결과 원문 관계 이식 경로이며, 전체 카드의 완료 기준을 아직 충족하지 않는다. 운영 DB·배포·실제 사용자 자료는 건드리지 않았다.

## 현재 구현

- `ieum-personal` version 1 gzip tar에 `manifest.json`과 Capture Markdown 파일을 담는다. archive의 경로·타입·헤더 checksum·파일 수·압축 및 해제 크기를 제한하고, manifest의 파일 SHA-256·UTF-8·중복 ID·미등록 파일을 검증한다.
- `0019`·`0020`은 공간 한정 run/row와 출처 ID 매핑을 저장한다. export 생성·다운로드와 import staging·dry-run·명시 적용을 분리한다. 계정·OWNER 권한은 각 단계에서 재확인하고 전체 export 생성과 import 적용은 최근 인증을 요구한다. 완료 후 다운로드는 24시간이 지나면 410을 반환한다. 같은 bundle 재업로드는 기존 유효 run을 재사용하고, 사용자별 유효 run 16개·합계 128 MiB를 transaction advisory lock으로 제한한다. 제한 검사 후 같은 잠금 안에서 파일을 기록해 동시 요청도 초과 저장하지 않는다. 전용 volume은 시작 시와 매시간 파일 수정 시각 25시간 초과분을 정리한다.
- 현재 Capture import는 원본 공간·ID를 sourceKey로 보존하고 원문을 새 불변 revision과 Unit으로 생성한다. 동일 번들·재수출 뒤 재이식은 중복으로 판단하며 제목/본문이 달라진 같은 출처는 충돌로 보고한다. previewHash가 달라지면 적용하지 않는다. 행별 명령 receipt·audit·상태를 저장한다.
- Archive는 전용 private `IEUM_TRANSFER_ROOT`가 없으면 API에서 503을 반환한다. v1 응답은 `scope=CAPTURES_ONLY`를 명시한다. 토큰·세션·인증 DB와 공개 Delivery 내용은 archive에 포함하지 않는다.
- version 2 묶음은 기존 Capture Markdown 외에 Task와 Event의 현재 상태·일정·시간대·원본 식별자를 manifest에 담는다. v1 묶음 import는 유지한다. v2 응답은 `scope=CAPTURES_TASKS_EVENTS`를 명시한다. 여러 테이블의 export 조회는 `REPEATABLE READ` snapshot으로 묶고, 현재 본문·날짜·시간대·종일/시간 지정 일정의 정합성을 staging 전에 검사한다.
- Task·Event는 source ID를 새 target ID에 매핑해 행별 명령 receipt·audit와 함께 이식한다. version 2에서는 Task의 Context/Unit 참조가 `MISSING_REFERENCE`로 미리보기·실패 행에 남는다. 참조를 지우고 Task를 성공으로 표시하지 않는다. 이미 매핑된 target이 삭제된 경우에는 새 레코드를 조용히 만들지 않고 `CONFLICT`로 보고한다.
- version 3 묶음은 Context의 현재 identity와 source revision을 추가한다. ACTIVE/ARCHIVED Context를 새 identity revision 1로 이식하고 원본 revision은 출처 매핑에 보존한다. Task의 Context 참조가 같은 묶음에 있으면 현재 권한 공간의 target Context ID로 remap한다. 참조할 Context가 없거나 충돌·실패하면 Task도 `MISSING_REFERENCE`로 남긴다. SUPERSEDED Context와 Unit 참조는 아직 이식하지 않는다. v1·v2 import 호환은 유지한다. v3 응답 scope는 `CAPTURES_TASKS_EVENTS_CONTEXTS`다.
- version 4 묶음은 Task 상태 전이의 version·이전/다음 상태·기록 시각을 추가한다. manifest에서 존재하지 않는 Task, 중복 전이 version, Task API가 금지하는 전이, 상태 연결 불일치, 최종 상태 불일치, 제공된 완료 이력의 `completionVersion` 불일치를 staging 전에 거부한다. 적용은 Task와 전이를 같은 행별 명령 transaction에 저장한다. 재이식 중복 판정은 현재 상태뿐 아니라 전이 목록도 비교한다. 대상 환경의 행위자 ID는 이식 명령 실행자를 기록한다. v1~v3 import 호환을 유지하고 v4 응답 scope는 `CAPTURES_TASKS_EVENTS_CONTEXTS_TASK_HISTORY`다.
- version 5 묶음은 Task 결과가 연결한 Capture와 완료 전이 version을 추가한다. 묶음 안의 Task·Capture와 해당 DONE 전이가 없으면 staging 전에 거부한다. preview와 적용은 같은 run에서 생성·중복 확인된 대상 Task/Capture ID로만 FK를 연결하며, 누락/충돌 시 결과 행만 실패로 남긴다. 결과 행은 별도 명령 receipt·audit와 원본 출처 매핑을 가진다. v1~v4 import 호환을 유지하고 v5 scope는 `CAPTURES_TASKS_EVENTS_CONTEXTS_TASK_HISTORY_RESULTS`다.
- version 6 묶음은 Capture의 현재 revision과 이전 불변 revision을 각각 Markdown·SHA-256·기록 시각으로 담는다. staging은 revision 1부터 현재까지 빠진 번호·중복·파일 누락·본문 위반을 거부한다. 적용은 한 Capture의 revision·기본 Unit을 한 명령 transaction에 저장한다. 동일 출처의 과거 본문이나 시각이 달라지면 현재 본문이 같더라도 `CONFLICT`로 보고한다. v1~v5 import 호환을 유지하며 v6 scope는 `CAPTURES_TASKS_EVENTS_CONTEXTS_TASK_HISTORY_RESULTS_CAPTURE_HISTORY`다. Archive의 256 파일 상한으로 현재 Capture와 과거 revision 합계가 255개를 넘으면 export는 실패한다.

## 남은 범위와 위험

Unit·Context 다중 관계와 과거 revision, SUPERSEDED Context, 문서·첨부·자료 묶음의 이식, Unit 및 문서 source FK의 안전한 remap, 데이터 용량을 넘는 다중 번들 처리가 남았다. 이전 v2/v3로 이식된 Task에는 원래 전이 이력이 없을 수 있으므로 v4/v5 재수출도 없는 이력을 복원하지 못한다. 프로세스가 중단된 상태에서 만료 파일 정리의 실제 시각은 보장하지 않는다. 현재 API는 설정한 전용 volume이 있을 때만 동작한다. 이를 개인 데이터 전체 export라고 표시하거나 BE-21을 VERIFIED로 올리지 않는다. `0019`·`0020`을 운영에 적용하지 않았다.

초기 quota 반례 실행은 변경된 backend `dist`를 다시 빌드하지 않아 파일 쓰기 전 검사 이전 코드가 로드되며 실패했다. backend build 후 동일 시험이 통과했고, 이후 전체 typecheck는 빌드를 포함해 수행한다.

읽기 전용 `security-review`가 무제한 staging과 파일 쓰기 전 quota 검사의 경쟁을 발견해 같은 transaction lock 안에서 quota→파일 쓰기→run insert로 수정했다. 읽기 전용 `change-review`가 공백/NUL 원문 staging과 같은 출처의 동시 적용 unique 충돌을 발견해 도메인 본문 검증과 출처별 advisory lock을 추가했다. 두 검토는 정적 검토이며 위 검증 명령은 main이 직접 실행했다.

v2 확장 읽기 전용 `security-review`가 UUID 대소문자 변형으로 출처별 잠금이 갈라지고 `ON CONFLICT DO NOTHING`이 중복 생성 사실을 숨길 수 있음을 찾았다. 출처 잠금·Capture sourceKey를 소문자로 정규화하고 Task/Event 신규 매핑에는 충돌 무시를 제거했다. Capture 매핑 충돌은 기존 target 일치 여부를 검사한다. 읽기 전용 `change-review`는 Task API에서 허용하는 `GMT`가 import에서 거부되는 계약 차이를 찾아 Task 시간대 검증을 일치시켰다. 두 반례에 대한 위 검증은 main이 직접 실행했다.

v3 확장 읽기 전용 `security-review`에서는 확정 보안 결함을 찾지 못했다. Context 생성은 서버가 정한 공간과 새 ID를 쓰고 Task 참조는 같은 묶음의 Context와 해당 공간의 이식 결과를 통해서만 연결되는 것을 확인했다. 실제 통합·단위 검증은 main이 실행했다.
읽기 전용 `change-review`에서도 v1/v2 호환 분기, Context 우선 적용, Task 참조 재매핑, 날짜·재수출 처리에서 확정 회귀를 찾지 못했다. 두 검토 모두 동적 테스트를 재실행하지 않았다.

후속 schema 대조에서 구조 분할은 `SUPERSEDED`와 null 단일 후속 ID를 허용한다는 사실을 확인했다. 이전 v3 입력 검증은 이를 거부해 export한 묶음을 staging할 수 없었다. 단일 후속 ID가 있는 상태가 `SUPERSEDED`여야 한다는 방향의 검사만 유지했다. 이 범위의 Context는 여전히 적용 시 `MISSING_REFERENCE`로 보고하며, 다중 후속 관계 이식은 남아 있다.

v4 읽기 전용 `security-review`는 제공된 DONE 이력의 마지막 전이 version과 `completionVersion`이 달라도 통과하는 경로를 찾았다. 잘못된 완료 결과 Capture가 다른 상태 전이에 연결될 수 있어 두 버전의 일치 검사를 추가했다. 이력이 아예 없는 과거 v2/v3 이식 Task는 원래 전이를 복원할 수 없으므로 별도 한계로 유지한다.
읽기 전용 `change-review`는 연결된 상태 문자열이라도 Task API의 금지 전이(CANCELED→DONE 등)를 직접 삽입할 수 있음을 찾았다. Task 서비스의 허용 전이표를 동일하게 호출하도록 해 staging에서 거부한다.
두 검토자는 보정된 국소 경로를 읽기 전용으로 재검토해 기존 지적이 해소됐고 새 확정 문제는 없다고 보고했다. 동적 검증은 main이 직접 실행했다.

v5 읽기 전용 `security-review`는 결과 참조가 해당 run의 매핑 대상만 사용하고 공간 경계·출처 잠금·DB FK/unique를 유지하는 것을 확인했으며, 확정 보안 결함을 찾지 못했다. Task 결과 적용은 기존 Task API의 row lock과 경쟁하지 않도록 대상 Task row도 잠근다. 동적 경쟁 반례는 아직 실행하지 않았다.
읽기 전용 `change-review`는 같은 묶음 내 두 결과가 하나의 Capture를 참조하면 둘 다 `NEW`로 미리 보일 수 있고, UUID 대소문자만 다른 참조가 거부되는 문제를 찾았다. manifest에서 Capture 결과 연결의 중복을 거부하고 관련 ID 비교를 정규화했다. 정상·반례 단위 테스트와 대문자 참조 API 통합 검증을 실행했다.

v5 후속 입력 검토에서 서로 다른 두 TaskResult가 같은 원본 출처(workspace ID·result ID)를 쓰면 둘 다 `NEW`로 미리 보인 뒤 첫 행만 적용되는 불일치를 확인했다. 당시 manifest 단계에서 출처 쌍 중복을 거부했으나, v6 재수출 검증에서 같은 공간의 원본·이식본이 합법적으로 동일 출처를 보유해 정상 bundle까지 거부함을 확인했다. v6에서 이 제한을 되돌리고 두 번째 결과를 preview `CONFLICT`로 표시해 사용자에게 실패 가능성을 미리 드러낸다. 기존 `4e81995` 보정은 이 수정으로 대체된다.
후속 보정에 대해 `pnpm --filter @ieum/backend build`, `npm run format:check`, `npm run lint`, `git diff --check`를 Node 24.18.0/macOS에서 각각 exit 0으로 확인했다.

v6 읽기 전용 `security-review`는 새 Capture ID 아래의 이력·Unit 원자 삽입, 해당 공간 RLS 조회, archive 경로·해시·연속성 검사를 확인했고 확정 보안 결함을 찾지 못했다. 동적 격리 DB 검증은 main이 직접 수행했다.
읽기 전용 `change-review`는 자기 공간 원본 Capture를 `NEW`로 복제하는 경로와 중복 출처 TaskResult의 미리보기·적용 불일치를 찾았다. 현재 공간의 원본 ID와 기존 출처 매핑 대상을 우선 조회해 revision 체인을 비교하고, 중복 출처의 두 번째 결과는 적용에서도 `FAILED/ORIGIN_DUPLICATE`로 고정했다. 격리 DB 통합 시나리오에서 원본 Capture `DUPLICATE`, 과거 본문 변경 `CONFLICT`, 중복 결과 `NEW/CONFLICT` 미리보기와 `IMPORTED/FAILED` 적용을 검증했다. 두 검토는 정적 검토이며 동적 검증은 main이 실행했다.
