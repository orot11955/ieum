# BE-03 · PostgreSQL migration·소유 범위·RLS

상태: **IMPLEMENTED** (2026-09-24 KST, Linux CI 확인 전). 선행 BE-02는 VERIFIED다. 아래 명령은 Node 24.18.0, macOS, 격리 Colima `ieum-be02`의 PostgreSQL 18.4 컨테이너에서 실행했다. 운영 DB·계정·배포는 변경하지 않았다.

## 구현과 경계

- 인증 vendor `auth` schema와 별도 `business` migration journal을 분리했다. `workspace`·`workspace_member`에 개인 owner unique, composite owner/member FK, auth user FK, 상태·버전 제약을 넣었다. 기존 auth-only 사용자 row를 유지한 upgrade와 빈 DB 순차 적용을 실제 PostgreSQL에서 확인했다.
- NOLOGIN `ieum_migrator`, `ieum_auth_runtime`, `ieum_application`, `ieum_delivery`를 분리했다. 업무 테이블 owner는 migrator이며 application은 CRUD grant만 받는다. 두 테이블에 FORCE RLS와 transaction-local workspace 정책을 적용했다. role SQL과 migration 절차는 [DB 안내](../../db/README.md)에 있다.
- `withWorkspaceTransaction`은 UUID scope를 검사해 같은 connection의 transaction 안에서 설정·해제한다. `assertApplicationDatabaseRole`은 앱 DB login의 superuser/BYPASSRLS/DDL·auth·migrator 겸임 및 전환 가능한 위험 역할을 거부한다. BE-04가 세션·membership/action 검사와 API 시작 연결을 구현하기 전에는 사용자별 종단 인가를 주장하지 않는다. 임의 SQL을 허용하는 계정에게 custom GUC만으로 인가를 보장하지 않는다.

별도 보안 검토가 앱 login의 임의 BYPASSRLS 역할로 `SET ROLE` 가능한 경로를 지적했다. 역할 검사를 보완하고 실제 PostgreSQL 반례를 추가해 5/5 재실행했다. 재검토에서 해당 경계의 추가 결함을 확인하지 못했다. 이는 운영 역할 구성이나 BE-04 세션 인가 검증을 대신하지 않는다.

`pnpm audit --audit-level high`는 lock 변경 후 한 차례 exit 0으로 확인했으며, 이후 동일 lock에서 registry DNS 실패(`ENOTFOUND`)로 재실행을 중단했다. 앞선 확인에는 기존 개발 의존성 `esbuild 0.18.20`의 moderate advisory 1건만 있었다. Linux CI DB job은 아직 미실행이다.

## 데이터 영향·복구

추가형 business schema만 격리 DB에 적용했다. 실제 DB는 미접근이다. 운영 적용에는 기존 role/schema inventory, backup, credential 분리, migration rehearsal과 별도 승인이 필요하다. 파괴적 down migration은 제공하지 않는다. 앱 코드 되돌림은 business schema를 읽지 않게 하는 것으로 가능하나 DB 복원은 별도 절차다.
