# BE-07 · Capture·원본 revision·ThoughtUnit

상태: **IMPLEMENTED** (2026-09-24 KST). 선행 BE-05와 CORE-01은 VERIFIED다. Node 24.18.0/macOS에서 격리 Colima의 PostgreSQL 18.4 및 HTTP 통합 시나리오를 검증했다. Linux GitHub Actions 결과는 아직 확인 전이다. 운영 DB·배포는 변경하지 않았다.

## 구현과 계약

- `business` migration 0003에 Capture 현재 pointer·source metadata, 불변 CaptureRevision, ThoughtUnit 현재 상태, 불변 ThoughtUnitRevision을 추가했다. workspace+revision 복합 FK와 지연 현재-pointer FK, sourceKind+sourceKey 중복 제약, 공간별 `FORCE RLS`를 적용했다. 애플리케이션 DB role은 revision row를 조회·삽입할 수 있지만 수정할 수 없으며 현재 pointer/상태 테이블도 필요한 열만 UPDATE한다.
- 원문 생성은 명시적 idempotency key로 receipt·감사와 함께 저장하며, 원문을 receipt/감사에 복사하지 않는다. 기본 quote unit은 UTF-16 `[0,rawBody.length)`를 참조한다. 개정은 새 원문 revision과 기본 unit을 추가하며 과거 revision/span/unit을 수정하지 않는다. 현재 분할은 원문 전체를 공백·겹침 없이 덮는 UTF-16 span을 요구하고 surrogate 중간 경계를 거부한다. 이전 unit은 superseded 상태로 남겨 분할 이력을 다시 열 수 있다.
- 개인 workspace의 Capture 생성·목록(cursor)·현재/과거 revision 조회·개정·수동 분할·보관을 Zod/OpenAPI/Nest API로 연결했다. 다른 workspace 원문은 404로 숨긴다. 읽기 응답은 `Cache-Control: no-store`다. sourceKey 중복은 별도 idempotency key여도 409다.
- 원문과 제목의 과거 값은 revision별로 고정한다. 원문 개정으로 Task 완료나 발행본을 갱신하는 경로는 만들지 않았다.

첫 BE-07 DB 실행은 단독 high surrogate가 입력 검증을 통과하는 문제를 찾아 1/9 실패했다. UTF-16 짝 검증에서 문자열 끝 `NaN`을 거부하도록 수정한 뒤 관련 테스트가 통과했다. 한 API 재실행의 목록 500은 변경 전 backend `dist`를 참조한 로컬 빌드 순서 문제였고, backend를 다시 빌드한 뒤 HTTP 1/1이 통과했다. CI는 API 테스트 전 Core→contracts→backend를 빌드한다.

별도 읽기 전용 보안 검토에서 세션→ACTIVE/OWNER→workspace 확인, 원문 revision 권한, bound query, no-store/오류 응답을 추적했고 재작업이 필요한 결함은 발견하지 못했다. 검토자는 테스트를 실행하지 않았다. Capture 요청과 계정 정지의 실제 경쟁은 BE-05의 동일 CommandCoordinator 잠금 경로 테스트로만 간접 확인했다.

## 미검증·데이터 영향·복구

합성 계정과 격리 Testcontainers DB만 변경했다. 운영 원문, 실제 import provider, 첨부, 브라우저, 복원·영구 삭제는 미접근/미구현이다. BE-07의 sourceKey는 입력된 출처 식별자만 저장하며 외부 수집 작업 자체는 제공하지 않는다. 목록 cursor의 API에는 한 번에 50개를 반환한다.

운영 적용에는 기존 DB/role inventory, backup, auth→role→business migration rehearsal과 별도 승인이 필요하다. 0003은 기존 row를 변경하지 않는 추가형이다. schema 삭제나 DB 복원을 자동 롤백으로 취급하지 않는다. Capture를 사용하는 클라이언트는 0003 migration 적용 전에는 배포하지 않는다.
