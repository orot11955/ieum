# M2 · 기록함과 원문

상태: **구현·로컬 검증 완료. 원격 CI와 사용자 인수는 아직.** 운영 DB·배포·실제 사용자 자료는 다루지 않았다. 기존 API(BE-07)를 그대로 쓰며 백엔드 코드는 바꾸지 않았다.

## 범위

기록 목록(W05, 보관 포함 토글은 URL `?archived=1`, cursor 페이지 "더 보기"), 새 기록, 상세(W06: 원문·단위·revision 이력, 지난 revision은 `?revision=N`로 읽기 전용), 수정(새 revision), 원문 나누기, 보관. 기록함 메뉴를 추가했다.

## 설계 결정

- **기록 수정은 자동저장하지 않는다.** 저장 하나가 revision 하나이므로 명시적 저장만 revision을 만든다. 작성 중 글은 화면에만 있고, 이탈(메뉴 이동·탭 닫기)하면 확인 창이 뜬다. 저장 직후 이동이 막히지 않도록 이탈 판단은 렌더링 상태가 아니라 ref에서 읽는다(처음 구현에서 저장 성공 직후 이동이 막히는 버그가 있었고 E2E가 잡았다).
- **버전 충돌:** `VERSION_CONFLICT`가 오면 작성 중 내용을 폼에 그대로 두고 서버의 최신 제목·본문을 보여 준다. 저장 버튼은 "최신 버전 위에 저장"으로 바뀌고, 그때 최신 버전을 기준으로 다시 저장한다. 조용히 덮어쓰지 않는다.
- **멱등 키:** 같은 내용의 재시도·더블클릭은 같은 키를 쓰고, 내용이 바뀌면 새 키를 쓴다(서버는 같은 키에 다른 본문을 거부한다).
- **분할:** 원문을 읽기 전용 텍스트 영역에 보이고 커서 위치로 나눈다. 브라우저는 줄바꿈을 LF로 정규화해 위치를 알려 주므로 저장된 원문(CRLF 포함 가능)의 UTF-16 위치로 되돌려 계산한다. 서버 규칙과 같이 이모지 중간, 처음·끝, 공백뿐인 조각, 100조각 초과를 클라이언트에서 미리 거부한다.
- **캐시 key**는 모두 `["user", 사용자 id, "captures", …]`로 시작한다(M1의 계정 격리 규칙).

M2 시나리오 12개(격리 PostgreSQL, 실제 API): 입력 검증 오류와 더블클릭 1건 생성·원문 바이트 단위 보존(이모지·줄바꿈·앞뒤 공백), 한글 IME 조합(CDP `Input.imeSetComposition`) 중 재렌더링, 저장 실패(503) 후 입력 유지·같은 입력 재시도 시 1건만 생성, 200KB 근처 본문 저장과 한도 초과 안내, 수정으로 revision 증가·지난 revision 읽기 전용, 이탈 확인(계속 작성/나가기), 두 탭 동시 수정의 충돌 처리, 이모지 중간 분할 거부와 3조각 분할 후 원문 보존, 보관 후 목록 제외·수정 불가·보관 포함 토글, 55건 생성 후 50건 단위 페이지, 다른 계정이 URL로 열 때 404와 빈 목록, 320px 폭 가로 넘침 없음.

## 미검증·제한

- 단위(unit)의 지난 revision을 열어 보는 화면은 없다. 분할 후 이전 unit revision 보존은 BE-07 DB 테스트가 보증하고, 여기서는 원문 보존과 새 단위 표시만 확인했다.
- 보관을 되돌리는 API가 없어 화면에도 없다(휴지통·복원은 BE-22 범위로 동결).
- CRLF 원문의 분할 위치 변환은 코드로 처리했지만 E2E로 검증하지 않았다.
- 스크린리더 실제 읽기, 강제 색상 모드, 모바일 실기기 키보드는 검증하지 않았다. 분할용 위치 지정은 커서 이동(키보드)으로 가능하다.
- 200KB 상한 근처를 넘는 초대형 본문의 렌더링 성능은 측정하지 않았다(60,000자 저장·표시만 확인).
- 목록은 갱신 시각순만 지원한다. 검색·필터는 M6.
- 원격 Linux CI와 사용자 ACCEPTED는 아직이다.
