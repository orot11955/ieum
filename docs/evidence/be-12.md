## 구현과 계약

- API `POST /api/v1/workspaces/{wid}/judgements`는 현재 OWNER·세션·Origin·정확한 Unit revision을 확인하고 202 요청/명령 receipt/감사/outbox를 한 transaction에 저장한다. `GET .../{id}`는 현재 권한과 요청 actor를 다시 확인해 상태와 후보 수·truncation을 반환한다.
- worker는 outbox 참조만 queue에서 받아 현재 actor 권한과 Unit 상태를 다시 확인한다. repeatable-read transaction에서 현재 활성 revision·Context·membership·관계를 묶어 읽고 Core snapshot을 검증한다. 긴 lexical 검색·측정·observe 판단은 transaction 밖에서 실행하고, 저장 직전 관련 revision과 권한을 재확인한다. 중복 실행은 같은 run 한 건으로 수렴한다.
- 제품과 Lab이 동일 `@ieum/core` exact lexical 구현을 호출한다. run에는 비공개 raw snapshot·input hash·retrieval·측정값·observe 결과·단계별 지연·profile 상태를 저장한다. replay는 저장된 feature를 재계산하지 않고 판단만 재생한다. profile watermark 값은 현재 소속·원문·고정 lexical model 입력에서 매번 다시 계산한다. BE-06 무효화 watermark가 뒤처지면 `LAGGING`으로 기록한다.
- 제품 경로에는 embedding provider와 cache가 아직 없다. 존재하지 않는 cache를 흉내 내지 않았으며 semantic/hybrid 제품 판단이나 자동 Proposal은 열지 않았다. 후속 cache 도입 시 source/model 변경 무효화 검증이 필요하다. 현재 lexical 경로에는 재사용 가능한 오래된 embedding이 없고 매 요청마다 권한이 적용된 입력을 새로 읽는다.
- 운영 반영 순서는 별도 관리자 역할로 business migration `0008` 적용, pg-boss schema/`judgement-run` queue 생성, queue grants 적용, 분리된 API/worker 역할 검증 후 코드 배포다. 운영 적용은 별도 허가와 inventory·backup·rehearsal이 필요하다.
