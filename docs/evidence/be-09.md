## 구현과 계약

- `business` migration 0005에 Task 독립 row, 불변 TaskTransition 이력, TaskResult→Capture 링크를 추가했다. Task는 제목/설명, TODO/IN_PROGRESS/ON_HOLD/DONE/CANCELED, optimistic version, PROJECT Context 및 현재 ThoughtUnit revision 출처를 저장한다. `origin_kind=EXPLICIT`은 수동 명령을 표시하며 추출 후보 승인 경로는 BE-14에서 별도 검증한다. Task가 참조한 원문 revision은 이후 원문 개정에도 유지된다.
- 기한은 NONE/DATE/INSTANT를 DB CHECK와 discriminated API schema로 분리한다. DATE는 PostgreSQL `date`를 `::text`로 읽어 브라우저/서버 시간대 변환이 없으며, INSTANT는 offset이 명시된 입력을 UTC instant와 IANA timeZone으로 보존한다. 시간대 없는 모델 후보는 명시적 확정 전 저장하지 않는다.
- 상태 전이는 전체 편집 폼을 재전송하지 않는 `baseVersion+targetState` 명령이다. 낡은 version은 409, 완료 연속 클릭은 같은 key replay 또는 다른 key의 version 충돌로 처리한다. 완료 시점/완료 회차를 별도로 두고, 재개·보류·취소를 이력에 남긴다. 완료 후 제목/기한을 고쳐도 완료 회차와 기존 결과는 유지된다.
- 결과 추가는 완료 회차당 하나다. TaskService가 같은 command transaction 안에서 Capture 모듈의 삽입 경계를 호출해 새 불변 원문 revision/기본 Unit과 TaskResult 링크를 원자적으로 만든다. DB unique와 sourceKey로 다른 key의 중복 결과도 거부한다. receipt/감사는 결과 원문이 아니라 resource ID·버전만 보관한다. 명시적 Task·Capture 기능에는 Core/provider 호출이 없다.
- workspace 포함 복합 FK, Task/전이/결과 세 테이블의 FORCE RLS, Task의 필요한 열만 UPDATE하는 애플리케이션 권한을 적용했다. Task 생성/수정/상태 전이/결과, scoped 목록(cursor·상태 필터)/상세를 Nest·Zod/OpenAPI에 연결하고 조회 응답에 `Cache-Control: no-store`를 설정했다.

첫 BE-09 Task 통합 실행에서 날짜형 기한이 `pg`의 DATE 파싱을 거쳐 서버 시간대의 전날 `Date`로 반환되는 구현 결함이 드러났다. Task 조회 SQL을 `due_date::text`로 수정해 원래 날짜 문자열을 보존한 뒤 전용 5/5 및 전체 DB 18/18이 통과했다. 최초 실패의 뒤따른 version·상태 실패는 첫 테스트가 중단되며 fixture 상태가 진행되지 않은 연쇄 실패였다.

## 미검증·데이터 영향·복구

합성 계정·격리 DB만 변경했다. 운영 Task·실사용 시간대 입력·브라우저 UI는 미검증이다. Task의 PROJECT Context는 선택 사항이며 등록 당시 active 상태를 확인한다. 추출 후보의 origin은 BE-14에서 승인된 Proposal과 함께 연결해야 하므로 이번 API는 명시적 수동 입력만 허용한다. 결과 Capture는 private 원문이며 공개 Delivery에는 포함되지 않는다. BE-11은 FE-02 선행으로 아직 시작할 수 없다.

운영 적용에는 기존 DB/role inventory, backup, 0005 migration rehearsal, BE-07/08 선행 migration과 API 배포 순서 및 별도 승인이 필요하다. 0005는 신규 테이블만 생성한다. 복구는 사전 백업과 별도 계획으로 수행하며 스키마 삭제를 자동 롤백으로 취급하지 않는다. BE-09 API는 0005 적용 후 배포해야 한다.
