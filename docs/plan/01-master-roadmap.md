# 01 · P0–P9 마스터 로드맵

## 1. 진행 원리

코어·백엔드·웹은 책임별 backlog로 분리하지만, **실제 개발은 사용자 기능별 세로 흐름**으로 완료한다. 백엔드 전체를 먼저 끝낸 다음 웹 전체를 만드는 방식은 사용하지 않는다. API 계약→domain/core 규칙→DB/command→web 상태→통합 반례→증거 순서로 기능 하나를 닫는다.

| 단계 | 목적 | 작업 ID | 결과물 | 사용자 가치 |
|---|---|---|---|---|
| P0 | 기준선·계약·프레임워크 spike | BASE-01–03, BE-01–02, FE-01–02, QA-01 | 고정 기준선, 실행 가능한 최소 패키지, 인증/편집기 호환성 증거 | 후속 기능을 추측하지 않고 첫 구현을 시작할 수 있음 |
| P1 | Core Lab 최소 실험 | CORE-01–08, QA-02 | 원문→candidate/abstain→근거→수동 선택→evidence pack CLI | 판단의 가능성을 UI와 DB 없이 측정 |
| P2 | 인증된 개인 공간 | BE-03–05, FE-03–04, QA-03 | 로그인·초대·MFA·개인 workspace·scope·command 기반 | 두 계정으로도 안전한 첫 앱 기반 |
| P3 | 수동 개인 관리 완결 | BE-07–11, FE-05–10, QA-04 | 기록/맥락/할일/결과/일정/위키·충돌 처리 | Core가 꺼져도 매일 사용할 수 있음 |
| P4 | 실제 판단·검색·추출 연결 | CORE-09–11, BE-06/12–14/26, FE-11–13, QA-05 | semantic/hybrid·job·제안/피드백·추출 승인·검색 | 기록 입력이 근거 있는 정리 후보와 관리 항목으로 이어짐 |
| P5 | 맥락 묶기·나누기 | CORE-12–13, BE-15, FE-14 | 구조 진단·before/after·승인·역변경 | 맥락을 목적에 맞게 정리하고 안전하게 되돌림 |
| P6 | 자료에서 통찰 문서로 | CORE-14–15, BE-16–18, FE-15–17, QA-06 | evidence pack·관점·outline·claim·선택적 모델 정제 | 출처를 확인하며 경험과 외부 자료를 문서화 |
| P7 | 검토·발행·Delivery | BE-19–20, FE-18, QA-07 | READY manifest·공개 snapshot·개정/철회·독립 소비자 | 외부 블로그와 분리된 발행 API 완결 |
| P8 | 이식·삭제·복원·운영 | BE-21–24, FE-19–20, QA-08 | import/export·purge·job/계정 운영·실제 restore | 재시작·장애·기기 변경 이후에도 데이터 유지 |
| P9 | 원래 목표 종단 인수 | CORE-16, BE-25, FE-21, QA-09 | 실제 품질·효용·성능·27화면·보안/복원 증거 | 기능 구현·품질·공개 운영을 구분해 최종 판정 |

## 2. 필수 의존 관계와 병렬화

```text
BASE-01 → BASE-02 → BASE-03
                    ├─ CORE-01 … CORE-08 → P1 평가/Replay
                    ├─ BE-01/02 → P2 인증·DB·command → P3 수동 관리
                    └─ FE-01/02 → 공통 UI/편집기 → P2/P3 실제 연결

P1의 측정 결과 + P3의 기록/맥락 → P4 실제 추천·추출
P4 및 semantic 구조 입력       → P5 맥락 구조 변경
P3 문서 기반 + evidence pack    → P6 수동 작업실
P4 추출/모델 검증 기반          → P6 선택적 생성 보조
P6 수동 작업실 + 첨부 공개 경계 → P7 검토·발행·Delivery
각 단계의 운영 기반 확장        → P8 이식·복원·운영
P1–P8 증거 + 실제 품질/효용     → P9 최초 컨셉 통합 인수
```

P0의 모든 spike가 끝나기를 기다려 CORE-01을 시작할 필요는 없다. `backlog.json`의 **개별 선행 작업**이 실행 조건의 정본이다. phases는 큰 진행 구간이며 숫자만으로 독립 작업을 직렬화하지 않는다.

P5 구조 추천 품질이 아직 낮아도 수동 P6/P7 개발은 진행한다. 다만 최초 목표에 포함된 구조 보조가 미완성인 상태를 full V1 완료라고 표시하지 않는다. 외부 모델이 없으면 우선 고정 artifact와 template로 테스트하고 실제 provider 연결은 해당 gate에서 검증한다.

권한·감사·기본 soft delete·관측은 P2부터 필요 기능에 포함한다. P8은 뒤늦게 보안을 붙이는 단계가 아니라 전체 데이터 수명과 운영 회복을 완결하는 단계다.

## 3. 구간별 세부 실행 묶음

### P0 · 기준을 바로잡고 불확실성이 큰 통합을 먼저 확인

1. BASE-01: branch/tree/문서 상태를 정리하고 Paper/Dark 보존 범위를 고정한다.
2. BASE-02/03: 최소 workspace와 계약·의존성 검사를 만든다.
3. BE-01/02: Nest/Fastify와 auth handler·schema를 실제로 시험한다.
4. FE-01/02: 디자인 상태와 editor JSON/IME/claim ID를 시험한다.

종료 조건은 커다란 skeleton이 아니라 **후속 구현자가 따라 쓸 실제 예제 한 개와 실패하는 반례**다. auth·editor·OpenAPI 호환성이 불명확하면 해당 adapter만 결정 기록으로 수정한다.

### P1 · 가장 먼저 코어의 존재를 증명

CORE-01/02로 입력 신뢰성을 만들고, CORE-03/04로 후보를 검색하고, CORE-05로 근거 있는 후보와 보류를 반환한다. CORE-06/07로 동일 실행을 재생·평가하고, CORE-08로 근거 묶음을 출력한다. 모델과 웹 없이 `기록→관련 맥락→근거→수동 선택→자료 묶음`이 끝나야 한다.

### P2 · 사용할 수 있는 개인 공간

BE-03 실제 DB 제약/RLS→BE-04 사용자/개인 공간→BE-05 receipt/감사 순으로 닫는다. FE-03/04로 로그인·온보딩·복구·세션 관리까지 연결한다. 이 단계에는 가짜 개인 기록·가짜 operator 권한을 넣지 않는다.

### P3 · 개인 관리의 첫 완결

권장 세로 순서는 **기록(BE-07/FE-05)→맥락(BE-08/FE-06)→할일·결과(BE-09/FE-07)→일정(BE-10/FE-08)→위키(BE-11/FE-09)→홈(FE-10)**이다. 위키가 처음 등장할 때 autosave/IME/충돌을 함께 구현한다. 미완성 editor를 먼저 배포하고 다음 단계로 미루지 않는다.

### P4 · 판단이 실제 제품에 붙는 구간

CORE-09/10으로 semantic/hybrid를 비교하면서 BE-06 job과 BE-12 snapshot bridge를 만든다. BE-13/FE-12로 후보/제안/노출/피드백을 닫는다. CORE-11/BE-14/FE-13으로 추출 후보를 승인된 업무 명령으로 연결한다. 일반 검색 BE-26/FE-11은 core 추천 정책과 분리한다.

### P5 · 구조 정리가 태그 편집을 넘어서는 구간

CORE-12 진단→CORE-13 대안 비교→BE-15 transaction/역변경→FE-14 before/after를 닫는다. 원문 1개에서 나눈 단위를 독립 근거로 세지 않으며, 공통 기록을 둘 다 유지하는 구조를 실제로 시연한다. 새 기록이 생긴 뒤 Undo에서 삭제하지 않고 충돌을 내는 반례까지 포함한다.

### P6 · 글을 정제하는 구간

먼저 모델 없이 BE-16/FE-15의 자료 선택·관점·outline·수동 편집을 완성한다. CORE-14/15는 형식·근거·readiness 검증을 담당하고 BE-17/FE-16은 모델 호출과 diff 적용을 담당한다. BE-18/FE-17로 첨부·public derivative 경계를 추가한다. 자료가 있는 문서와 그럴듯한 문장을 생성한 문서를 구분한다.

### P7 · 실제 공개 계약을 닫는 구간

BE-19/FE-18로 seal→review→publish→revise→withdraw를 만든다. BE-20은 공개 projection만 읽는 Delivery 모듈과 role을 만들고 QA-07은 별도 소비자로 확인한다. 내부 ORM 모델/세션을 공유하는 데모를 독립 API 검증으로 취급하지 않는다.

### P8 · 데이터 수명과 운영 복구

Import/Export, 휴지통/영구 삭제, 계정·job·로그·설정을 feature별로 마감한다. DB만 복원하지 않고 assets·schema·credential·삭제/철회 상태까지 검토한다. 실제 새 환경에서 read 검증을 수행한 후 QA-08을 완료한다.

### P9 · 통합 인수

CORE-16의 실제 품질·정리 효용, BE-25의 실측 성능, FE-21의 화면 상태를 종합한다. 제한이 있는 기능은 상태표에 남긴다. 원래 목표를 새 이름의 더 작은 MVP로 바꾸어 완료 처리하지 않는다.

## 5. 완료 상태 정의

`PLANNED → IN_PROGRESS → IMPLEMENTED → VERIFIED → ACCEPTED`를 구분한다. 현재 BASE-01–03과 CORE-01/02는 VERIFIED, 나머지 70개는 PLANNED다. 상태의 정본은 `backlog.json`이다. 카드 완료 판정에는 VERIFIED/ACCEPTED 증거가 필요하고 다음 의존 작업이 안전하게 사용할 수 있어야 한다. 코드만 존재하는 상태, fixture만 통과한 상태, 실제 품질이 검증된 상태, 공개 운영 가능한 상태를 하나로 합치지 않는다.

전체 과제를 한 번에 한 agent에게 맡기지 않는다. BASE-01–03과 CORE-01/02는 검증 완료 상태다. CORE-03–08을 우선 진행하며, BE-01/02·FE-01/02의 P0 spike도 개별 선행 조건에 맞춰 진행할 수 있다. 카드가 준비되면 선행관계의 **작은 카드 한 개**부터 실행하고, 성공한 기능을 커밋한 뒤 다음 카드로 이동한다. 구체적인 진행 순서와 gate는 [09 · 단계별 구현 순서](09-implementation-sequence.md)를 따른다.
