# IEUM 제로베이스 검토 · 2026-09-22

## 검토 기준과 한계

검토 대상은 기존 프로젝트 논의의 사용자 요구, 이 세션의 판단 로직 제안, 그리고 저장소 `main`의 기존 8개 Markdown 문서다. 저장소 기준 commit은 `2d14454cc587b9faf5d8fd8b8f42513bdb0f5b38`이다. 기존 문서는 Git 이력에서 보존한다.

실행 코드·실사용 평가셋·프로파일링 결과는 검토 시점 저장소에 없었다. 따라서 이번 결과는 **설계 재검토와 검증 계획**이며, core의 유효성이나 속도를 입증한 보고서가 아니다. 대화에서 제안된 수식과 수치를 기존 구현의 실측 사실처럼 취급하지 않는다.

## 결론

이음의 제품 가설은 유지한다. 다만 첫 검증 대상을 `정교한 6-evaluator 엔진 구현`에서 **다시 찾기와 근거 보존이 실제 수고를 줄이는지 확인하는 작은 수직 흐름**으로 바꾼다. 복잡한 설명이 붙은 가중합을 처음부터 정답으로 정하지 않는다.

유지할 것은 원본 보존, 다중 맥락, 설명 가능한 연결, 승인 후 변경, TS 중심 구현, 재현 가능한 비교다. 변경할 것은 점수의 의미, 초기 구현 순서, 의미 검색 도입 시점, 평가셋과 성능 측정 방법이다.

## 중요한 설계 결함

### 1. 평균의 일치가 판단의 정확성을 보장하지 않는다

Identity와 Corpus가 같은 단어를 중복 사용하면 서로 독립적인 증거가 아니다. 둘이 같은 이유로 틀려도 분산은 작다. `0.65 × evidenceMass + 0.35 × agreement`는 정의한 진단 수치일 뿐 정답 확률이 아니다.

또한 `weight × reliability`를 합계로 나누면 강한 내용 증거가 없어도 최근성 하나가 점수를 지배할 수 있다. 새 설계는 내용 증거의 가용성을 별도 gate로 사용하고, 결측 때문에 남은 가중치를 후보별로 조용히 증폭하지 않는다. 확률 보정의 의미는 [공식 calibration 문서](https://scikit-learn.org/stable/modules/calibration.html)를 참고한다.

### 2. 다중 연결과 단일 선택을 혼동했다

A와 B가 모두 유효한 맥락이면 두 점수가 비슷한 것은 정상이다. Attachment는 후보별 적합성으로 판단하고 primary 선택만 경쟁 후보와 비교한다. 하나를 primary로 바꾸었다고 다른 secondary까지 틀렸다는 라벨을 생성하지 않는다.

### 3. 검색 실패를 가중치로 해결할 수 없다

정답이 후보에 없으면 evaluator를 늘려도 복구할 수 없다. 반대로 모든 맥락이 후보인 작은 예제의 Recall@10은 탐색 능력을 증명하지 않는다. 검색 recall, 후보 내 정렬, 추천 정책, 사용자 효용을 각각 평가한다.

### 4. 과거 판단에 미래의 지식을 넣을 위험이 있다

완성된 ContextProfile, 나중에 붙인 관계, 수정된 정답 소속을 과거 query에 사용하면 결과가 부풀려진다. 모든 Replay는 관측 당시 snapshot으로 평가한다. 현재 ThoughtUnit과 같은 원본의 파생물이 자기 자신의 검색 근거가 되지 않게 한다.

### 5. 한국어와 의미 이해의 역할을 과소평가했다

문자 n-gram은 어휘 baseline이지 한국어 의미 이해를 보장하는 장치가 아니다. `Intl.Segmenter`의 경계 분할과 형태소 분석도 동일하지 않다. 기본 PostgreSQL 검색 랭킹을 BM25라고 부르지 않는다. PostgreSQL 문서는 기본 랭킹으로 `ts_rank`와 `ts_rank_cd`를 설명한다. [Unicode](https://unicode.org/reports/tr29/) · [PostgreSQL](https://www.postgresql.org/docs/18/textsearch-controls.html)

### 6. 묶기·정리하기가 진실 판정으로 넘어가면 안 된다

반론은 같은 주제에 매우 관련 있는 기록일 수 있다. 유사도나 반복된 주장을 근거의 독립성·사실 확인으로 해석하지 않는다. 글의 준비도는 연결 점수와 별도이며, 미확인 주장과 열린 질문을 그대로 보존한다.

## 새 구현 방향

`M0 평가 계약 → M1 lexical 수직 실험 → M2 semantic/hybrid 비교 → M3 영속 저장·승인 UI → M4 구조·파생`으로 진행한다. 초기 baseline이 약해도 M2에서 핵심 가설을 검증할 수 있다. 이 순서는 단순히 미래 기능을 금지하는 규칙이 아니라, 가장 싼 실험으로 다음 투자 여부를 결정하는 순서다.

로컬 프로세스 하나, 파일 fixture, 작은 TS core로 출발한다. DB·HTTP·UI·모델 런타임은 경계를 두되 구현하지 않은 미래 시스템의 stub을 대량 생성하지 않는다. [실행 계획](../plan/02-core-plan.md)에 각 단계의 산출물과 중단/수정 조건을 정의했다.

## 아직 답하지 못한 질문

실제 기록에서 lexical보다 의미 검색이 얼마나 나은지, 사용자에게 유효한 Context의 크기와 개수가 무엇인지, 어느 수준의 추천 빈도가 부담인지, source pack이 글 정리 시간을 줄이는지는 데이터가 필요하다. 특정 모델이나 가중치가 정답이라고 확정하지 않는다.

이 문서의 결정은 다음 실험을 위한 설계 선택이다. 임계값·정확도·속도 목표는 결과가 쌓이면 버전 관리하며 수정한다.
